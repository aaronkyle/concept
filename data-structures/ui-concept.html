file metadata editor concept

This historical interface mockup explored which technical and descriptive information we wanted to expose and edit as file metadata. The fields below do not load or save data; they preserve an early expression of the requirement.

The idea is now being developed through Archive, where original files, extraction results, curated metadata, and access decisions can remain distinct, and Docs Repo, where people can work with files, previews, metadata, and revisions in a project context.

how the concept has changed

The original form flattened tool output and human description into similar text inputs. The renewed model keeps the visual goal—technical and descriptive information available together—while giving each value a source, authority, history, and publication boundary.

original field current interpretation
FileName and Directory Original names and storage locations are intake or administrative facts. They are not durable identity and may have different visibility.
FileType, FileSize, and PageCount Technical observations should normally be read-only and identify the tool, version, input checksum, and observation time.
Title, Author, and Keywords Embedded values remain source observations. Curated descriptions, identified agents, and controlled subjects are separate assertions that can cite or reject them.
CreateDate, CreationDate, ModDate, and MetadataDate Similar tag names can carry different provenance and meaning. Preserve the raw tag namespace and map only reviewed values to defined project dates.
DocumentID An embedded document identifier is not automatically the managed file, work, version, or external catalog ID. Store the scheme and entity being identified.

A current editor should show conflicting observations, the preferred curated value, revision history, and the exact public view before a change is approved. Archive and Docs Repo are where those requirements now develop.
