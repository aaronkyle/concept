# identifiers, names, and controlled values

An identifier lets the system refer to something consistently. A name helps a person recognize it. A path tells software where a representation is currently stored. A classification places it within a governed conceptual scheme. These values sometimes look alike, but they have different responsibilities and patterns of change.

Much of the former `scratch-notes.md` concerned database casing and elaborate article filenames. The durable response is to separate identity from display and location, then establish simple conventions for each layer.

## different values answer different questions

| value | question answered | example | expected change |
| --- | --- | --- | --- |
| internal identifier | Which entity does this system mean? | UUID or application-issued ID | should remain stable |
| preferred label | What should people call it here? | “Lower Mekong region” | may be corrected or translated |
| alternate label | What other name may identify it to a person? | abbreviation, former name, local name | may accumulate or expire |
| external identifier | Which record does another authority mean? | DOI, ORCID iD, ROR ID, ISBN | normally stable within its scheme |
| checksum | Which exact bytes are these? | SHA-256 digest | changes when any byte changes |
| filename | How is this file presented in one directory or download? | `report-2001.pdf` | may change for usability |
| path or object key | Where is this representation currently stored? | `received/2026/07/object.pdf` | changes during movement or reorganization |
| vocabulary code | Which governed concept is intended? | `evaluation_report` | governed through vocabulary versions |

Do not make a display name, path, or mutable business property the primary key merely because it is currently unique.

## internal identifiers

A good internal identifier is unique within a stated scope, stable for the entity's lifetime, never reassigned, and independent of properties likely to change. It may be an integer generated by one database, a UUID, or a URI under a domain the project controls.

[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562) defines current UUID formats. Random UUIDv4 values work without a central allocator; time-ordered UUIDv7 values can improve ordering and some database index behavior. The choice should be standardized per application, and IDs should be treated as opaque—software should not infer business meaning from their characters.

An identifier alone does not prove authenticity, authorization, or persistence. A UUID copied into two conflicting records still requires governance, while a URL remains persistent only if someone maintains its resolution.

## external identifiers

External identifiers improve connection and reduce accidental duplication when the issuing authority matches the entity:

- DOI for registered research outputs and other citable resources;
- ORCID iD for researchers who identify themselves through ORCID;
- ROR ID for research organizations;
- ISBN for editions of books and ISSN for continuing publications;
- authoritative geographic, administrative, or statistical codes for places and areas; and
- provider or source-system identifiers needed to reconcile an import.

Store the scheme, value, source, and verification state. Do not strip a qualified identifier down to a bare string whose namespace is unknown. Do not assume two records are identical merely because one name resembles another, and do not silently merge conflicting external identifiers.

Some sources supply unstable record numbers or URLs. Preserve them as source identifiers or locators without promoting them to permanent global identity.

### identifiers that resemble numbers

Telephone numbers, postal codes, account references, and similar values may
contain digits without representing quantities. Store them as identifiers rather
than numbers: leading zeroes, prefixes, separators, and extensions can be
meaningful, while addition and numeric ordering are not.

For telephone numbers, preserve the value as supplied, record country or context
when known, and maintain a separate normalized value for matching or dialing.
[ITU-T E.164](https://www.itu.int/rec/T-REC-E.164/en) defines the international
public numbering format, but extensions, local dialing conventions, uncertainty,
and a person’s preferred display still require separate treatment. An interface
should not reject a valid contact merely because a simplistic numeric field or
country-specific mask cannot represent it.

## checksums and file identity

A cryptographic checksum is a strong identifier for a byte sequence and a useful integrity check. It can reveal that two differently named files have identical bytes or that a stored object changed. It cannot establish that two different PDFs express the same intellectual work, that the bytes are trustworthy, or that one file supersedes another.

Archive should therefore distinguish:

- the managed file-object ID;
- one or more recorded checksums with algorithm and calculation event;
- original and current names;
- storage locations and versions;
- relationships to a work, edition, dataset, or other intellectual resource; and
- duplicate, derivative, replacement, and publication relationships.

This allows deduplication without collapsing distinct capture events or provenance.

## filenames and paths

Keep the original filename as an intake fact. If the system generates a safer or clearer working name, record it separately rather than overwriting the evidence of how the file arrived.

The older notes proposed embedding journal initials, year, volume, issue, pages, and author names in every article filename. That can help a person scanning a folder, but it duplicates bibliographic metadata, creates long fragile names, handles multiple contributors poorly, and forces renaming when a citation is corrected.

Prefer a short generated name that is unique within its intended directory or export. Depending on the context, it may combine a stable short ID with a readable slug:

```text
01jz8n6m2t-report-title.pdf
```

Use portable Unicode deliberately, avoid filesystem control characters and ambiguous separators, preserve the extension when it describes the representation, and test case behavior on supported platforms. A date prefix is useful when chronological sorting is genuinely meaningful. Do not encode access level, workflow state, or the only copy of important metadata in a filename.

The [file-first storage discussion](../data-storage/file-first-and-portable-formats.md) explains where original, canonical, derived, and published files belong. A manifest should connect their paths to stable IDs and checksums.

## field and database names

SQL engines differ in how they fold unquoted identifiers and treat quoted or filesystem-backed names. The former scratch page cataloged individual engine behavior; that detail belongs in each engine's current documentation and is a poor foundation for a portable application model.

For schemas we control:

- use one documented convention consistently, commonly lowercase `snake_case` for SQL and portable data fields;
- avoid names that differ only by case;
- avoid quoted SQL identifiers unless a real requirement outweighs portability costs;
- avoid reserved words, punctuation, spaces, and names whose meaning depends on capitalization;
- give foreign keys names that reveal the relationship, such as `source_file_id` rather than a generic `id2`;
- spell out ambiguous abbreviations and include units in the schema or field name where appropriate;
- do not silently reuse a field after its meaning changes; and
- map external field names at the import or API boundary instead of distorting the internal model.

Field naming style is less important than stable meaning. A data dictionary should define the concept, type, units, null semantics, allowed values, source, and examples for each field.

## labels and multilingual names

Names are data with their own context. A person, organization, or place may have preferred, alternate, historical, transliterated, abbreviated, and language-specific names. Preserve the source form and language where known. Do not force all names into a culturally specific `first_name` and `last_name` structure or assume an organization has one timeless English label.

A label record may need:

- the text and language or script;
- whether it is preferred, alternate, hidden, former, or an abbreviation;
- its source and responsible authority;
- dates or jurisdiction in which it applies; and
- its relationship to other identified entities after a rename, split, or merger.

Search can normalize case, accents, punctuation, and spacing without replacing the curated display form.

## controlled values

A controlled vocabulary prevents routine variants such as `In review`, `in-review`, and `reviewing` from becoming different states. Each concept should have an identifier or code distinct from its label.

A useful vocabulary entry can include:

- stable code or URI;
- preferred and alternate labels with language;
- definition and scope note;
- status such as proposed, active, deprecated, or replaced;
- broader, narrower, or related concepts;
- mappings to external vocabularies;
- effective dates and vocabulary version; and
- the authority responsible for change.

The [SKOS standard](https://www.w3.org/TR/skos-reference/) provides these patterns for taxonomies, thesauri, subject headings, and other knowledge-organization systems. A simple versioned JSON or table can be enough for an application; SKOS becomes valuable when schemes must be exchanged, mapped, or expressed in several languages.

## document types and citation types

The old document inventory combined BibTeX entry types with project-specific categories such as policy, evaluation study, loan agreement, operational update, and terms of reference. They answer different questions:

- a **citation or resource type** describes the form needed for bibliographic exchange, such as journal article, report, book chapter, dataset, or thesis;
- a **document genre** describes what kind of artifact it is within the domain, such as policy, impact assessment, agreement, or operational guide; and
- a **project role** describes how a team uses it, such as evidence, background, deliverable, reference, or working draft.

Maintain these as separate properties and allow more than one classification when appropriate. A policy can be published as a report; a technical report can serve as evidence in one project and background in another. Store the vocabulary, code, assertion source, and review state rather than using one overloaded `type` field.

## workflow states are not descriptions

Statuses such as `received`, `extracted`, `under_review`, `approved`, `published`, and `withdrawn` describe process state. They should not replace descriptive types or access decisions. A record can be approved for internal use and still prohibited from public release.

Define valid transitions, the authority required for each transition, and the event produced. Keep publication, sensitivity, retention, and review state separate when they can vary independently.

## merges, splits, and replacement

Entity resolution requires reversible decisions. When two records are merged:

- preserve both old identifiers as aliases or redirects;
- record who decided, when, why, and on which evidence;
- combine assertions without hiding conflicts;
- update derived indexes and relationships; and
- retain a means to reverse an incorrect merge.

When one record is later understood as several entities, issue new IDs and record the split. Do not change the meaning of the old ID silently. Similar rules apply to vocabulary concepts that are deprecated, replaced, broadened, or divided.

## a design checklist

1. Does each identifier have a stated scheme and scope?
2. Can its entity's name, path, owner, or status change without changing the ID?
3. Are byte identity, intellectual identity, and record identity distinguished?
4. Are external identifiers stored with their authority and verification state?
5. Can labels represent language, alternatives, history, and uncertainty?
6. Do controlled concepts have codes and definitions distinct from display labels?
7. Are resource type, domain genre, project role, workflow state, and access level separate?
8. Will naming conventions behave consistently across the required database engines and filesystems?
9. Can old identifiers continue to resolve after a merge, split, replacement, or migration?
10. Can a complete export retain these distinctions outside the application?

Stable identity allows everything else to change honestly.
